## Purpose

说明 schema v3 → v4 及版本化凭据引用升级的操作边界，以及如何恢复匹配的旧数据库与凭据状态。本说明不提供秘密导出功能；尚未完成 Windows 固定内核、注册表和桌面验收时，不交付本次数据库升级。

## Upgrade Procedure

1. 记录原应用版本、源码提交、Windows 版本和安装路径。在原版本中停止代理，确认系统代理恢复成功，然后通过托盘退出应用。存在恢复提示时先解决，不能带着未确认的系统代理归属继续升级。
2. 确认应用与受管内核已退出，再备份完整应用数据目录。数据库文件为 `config.sqlite3`，目录由 Tauri `app_data_dir()` 解析，应用标识为 `com.socksproxy.desktop`；以实际用户目录为准，不假定固定盘符。若 SQLite 存在 `-wal`、`-shm` 或事务日志，保留完整现场并在关闭数据库后做一致性备份，不只复制打开中的主文件。
3. 单独确认认证凭据可恢复：保有原用户名/密码，或有经过验证、受访问控制保护的系统凭据备份。应用便携导出不含密码，不能替代这一步；本应用不生成明文凭据备份，也不保证 Windows 系统备份工具能恢复任意凭据条目。无法恢复原凭据时，不能承诺可回退。
4. 保留旧安装包和升级前数据库备份，然后安装同一提交构建的新版本。首次启动先取得单实例租约，恢复遗留系统代理、清理受保护运行目录、恢复配置事务，再升级旧凭据引用；此前不能写配置或接管代理。
5. 成功升级后检查档案、规则、默认出口、认证和启动项行为。数据库结构版本为 4，配置中的内部凭据引用改为随机版本化条目；旧条目在提交后清理。记录应用版本和验证结果，不把无秘密导出内容不变理解为内部存储未变化。

## Interrupted Upgrade or Commit

恢复日志和配置提交标记位于 SQLite，秘密仅位于系统凭据存储。不要自行编辑 `user_version`、内部引用、恢复日志或受管进程归属标记。

- 配置尚未提交：恢复旧配置和启动项，清理未提交的新凭据。
- 配置已经提交：保留新配置和新凭据，完成旧凭据清理；不能回写旧配置。
- 恢复遇到外部启动项修改或缺失的新凭据：保留现场和日志，应用继续提供读取及脱敏错误，但阻止写入和新接管。核对原值与预期值、解决归属或凭据问题后使用“恢复网络”重试，或完全退出后重新启动。

恢复失败时先复制完整应用数据现场并记录错误码、版本及时间。不得把密码、控制密钥或带秘密的临时内核配置附到公共日志、Issue 或截图中。

## Backout Procedure

1. 在新版本中停止代理并完成恢复。若无法完成，保留恢复现场，先解决系统代理与进程归属；不要同时启动旧、新版本。
2. 通过托盘退出，确认进程已结束。备份当前新版本数据用于故障分析，再把升级前完整数据备份恢复到对应应用数据目录。恢复配套日志文件时必须属于同一备份时点，不能与当前数据库混用。
3. 安装旧版本后，保持代理停止，核对旧档案和旧内部引用。恢复匹配的系统凭据条目，或在旧版本中显式重新输入原用户名/密码。成功升级已删除旧 ID 条目，因此只恢复旧数据库通常仍会缺少凭据；新版本随机条目不能冒充旧 ID 条目。
4. 检查认证、规则、默认出口、系统代理和启动项，再允许旧版本接管。启动项实际命令与安装路径有关，不能只依据布尔开关认定匹配。归属不明时保留第三方值。

仅替换旧可执行文件会遇到数据库版本拒绝；不要通过降低 `user_version` 绕过版本检查。无密码导出不能恢复凭据，也不包含系统代理所有权日志，不能作为完整回退备份。

## Rehearsal Evidence

`configuration_crash_tests::upgrade::previous_database_and_matching_credentials_are_required_for_safe_backout` 使用真实 schema v3 SQLite 夹具、配置服务和运行时协调器升级为 v4，验证旧引用被版本化、旧条目被清理及便携导出不变。测试调用与生产相同的版本门禁，按旧版本支持上限 3 模拟旧二进制，确认拒绝新数据库且不修改文件；恢复旧数据库后仍缺少旧凭据，再恢复独立合成凭据状态才恢复一致性。

该演练在测试隔离目录使用合成凭据，模拟受保护备份或用户重新输入；不读取真实系统凭据，不是 Windows 系统凭据备份工具的验收。真实 Windows 安装路径、注册表、NSIS/WebView2 和凭据存储验收仍见 `tasks.md` 的目标平台任务。
